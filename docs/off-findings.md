## 8. Recommendation for the app data model

Based on the numbers above (unbiased hit rate 78/79 (98.7%); NL name 41.0%, FR 87.2%, brand 97.4%, quantity 92.3%, image 98.7% of hits):

1. **Keep the canonical EAN-13/EAN-8 as the only primary key.** Same EAN ⇒ same OFF record at every store, so store is an attribute of a sighting/price, never of the product key.
2. **Add an optional local `group`/canonical-name field** (e.g. `nutella`) only as a user-level link between EANs: different sizes/pack types are different EANs with similar but not identical names (section 5), and the same-labelled product could carry different EANs at different stores (section 4 lists 0 such cases in this fixture). Do not try to infer it from OFF.
3. **Store user-override names** (`userName`) separate from the cached OFF data, because OFF names carry suffixes, caps or wrong quantities (section 6) and misses need a manual name anyway. Display precedence: userName → OFF name chain.
4. **Name fallback chain nl → fr → en → generic** (as `Lib.pickName`, after canonical `product_name`), with the caller's UI language first; no single language field is complete (section 3).
5. **Display `brand + quantity` next to the name** (separately from the name) and treat quantity as untrusted when ≤1 g or missing; prefer the fixture/user value then.
6. **Flag variable-weight (2x) codes** (OFF coverage is spotty and not authoritative; show the OFF name only as a hint); for OFF misses (esp. private label) fall back to manual naming and optionally offer an OFF contribution link. Cache snapshots locally and tolerate 503/429 with retry.
